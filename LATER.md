# LATER

What Loam does not do yet, and what it is not going to do here.

Three sections, and the difference between them matters if you are thinking of sending a patch:

- **[Help wanted](#help-wanted)** — real gaps. Pull requests welcome; several are small.
- **[Known limitations](#known-limitations)** — things that will surprise you, with the reason and
  the shape of the fix.
- **[Not planned for this repo](#not-planned-for-this-repo)** — deliberately outside the boundary.
  Please do not spend a weekend on one of these without opening an issue first.

## Help wanted

### Column types Loam does not generate

`bytea`, `inet`/`cidr`, `interval`, and array columns are left to their database default. A nullable
or defaulted column of one of these is skipped with a warning; a `NOT NULL` one with no default is
reported, because writing a guess into it would be worse than saying so.

Each needs its own realistic-value story. They are independent of each other, so this is four
separate small changes rather than one big one — a good first contribution.
[`docs/CONTRIBUTING.md`](docs/CONTRIBUTING.md#support-a-new-column-type) has the recipe: four files,
about fifteen lines.

### `GENERATED ALWAYS AS IDENTITY` primary keys

Postgres rejects an explicitly supplied value for such a column, so the seeder cannot assign those
keys — and therefore cannot record them for child rows to reference. The column is skipped with a
warning. `serial`/`bigserial` and `GENERATED BY DEFAULT AS IDENTITY`, which between them cover almost
every real schema, work normally.

**The fix:** omit the column from the `COPY` and read the generated keys back with a follow-up
`SELECT` to fill the foreign-key pool. It costs one extra round trip per table.

### Unique constraints are not modelled

Generated values are not de-duplicated against a unique index. Columns that look like natural keys —
anything matching `email`, `sku`, or `code` — get a per-row counter woven in, and that counter is the
last thing surrendered when a value has to be trimmed to fit, so those stay distinct wherever the
column is wide enough.

Two gaps remain:

1. A `UNIQUE` constraint on some other random-valued column can still collide and fail the batch.
   **The fix:** read unique constraints during introspection and guarantee uniqueness for exactly
   those columns.
2. A column too narrow to hold a counter cannot be unique across a large seed at all — a
   `varchar(2)` has a few hundred possible values. That is arithmetic, not something a generator can
   fix. **The fix:** warn that the column is too narrow for the requested row count.

### Composite primary keys get correlated values

A composite primary key is generated unique, but its columns come from one counter, so a row looks
like `(tenant_id=1237, user_ref=1238)`. Valid and unique, but unrealistic — real data has many rows
per tenant.

**The fix:** make the leading column low-cardinality and the trailing one unique within it, which
needs the generator to understand a key's *shape* rather than its columns. Realism polish, not
correctness.

### Template-database fast reset

Make `reset` near-instant instead of truncate-then-reseed:

1. On the first seed, seed into a dedicated database such as `appdb_seed_template`.
2. Mark it a template: `UPDATE pg_database SET datistemplate = true WHERE datname = '…';`
3. `reset` then runs `DROP DATABASE appdb; CREATE DATABASE appdb TEMPLATE appdb_seed_template;`

Both statements require **no other session connected**, so the pool must be fully closed first and
connections opened against `postgres`/`template1`; expect to force-close stragglers with
`pg_terminate_backend` filtered on `datname`. The connection-eviction handling is where this is
actually hard — that, not the SQL, is the work.

### Pre-pull images on first run

Start `docker compose pull` ahead of, or in parallel with, the first `up`, so a cold machine does not
spend most of its time budget downloading Postgres. Needs care not to interleave its output with the
summary block.

### Run the project's own migrations

Loam assumes the schema already exists. A project that creates its schema with
`migrate`/`alembic`/`rails db:migrate` needs those run between `loam up` and `loam seed`.

Detecting and running a project's migration command means recognising a dozen tool conventions and
deciding when the schema is "settled". Worth doing well or not at all.

### Parallelise startup and seeding

Overlap the work: begin seeding as soon as Postgres answers, while app containers are still booting,
and generate rows for independent branches of the dependency graph concurrently. Parents must still
be committed before children, so this needs the topological order to drive a worker pool rather than
a simple loop.

### Other databases, and other runtimes

MySQL, SQLite, SQL Server. Introspection, type mapping and bulk load are per-engine, so each is a
substantial project rather than a patch — but they are squarely in scope and a well-made one would be
very welcome. Please open an issue to discuss the approach before writing it.

The same goes for **Kubernetes** as an alternative to Docker Compose. That one needs the runtime to
sit behind an interface first; say so in the issue and we can do that part together.

## Known limitations

### Two stacks from the same repo collide on published host ports

Every `up` gets its own Compose project, so containers, networks and volumes are genuinely isolated.
Host ports are not: a compose file that publishes `5433:5432` binds that port on the machine, so a
second `up` of the *same* repo fails with an address-already-in-use error from Docker before Loam
gets a say. Isolation across *different* repos, or copies with different published ports, works
today.

**The fix:** stop publishing the compose file's fixed ports, let Docker assign ephemeral ones, then
read the real port back with `docker compose -p <project> port db 5432`. Rewriting a user's port
bindings is a bigger behaviour change than it looks, which is why it has not been done. Worth
revisiting if anyone genuinely wants two copies of one repo up at once.

## Not planned for this repo

Loam is an open-source tool for creating a seeded, throwaway database and the stack around it. There
is also a commercial product built on top of it. The list below is the boundary between them.

None of this is a judgement on the ideas — several are good. It is here so that nobody spends a
weekend on something that would then be declined. **If you want to work on one of these anyway, open
an issue first and we will talk about it honestly** rather than after the fact.

| Area | Why not here |
|---|---|
| Pre-authenticated sessions, persona login, `storageState` injection | Part of the commercial product |
| Copy-on-write snapshots and point-in-time state branching | Part of the commercial product. The [template-database reset](#template-database-fast-reset) above is the open-source version of fast reset and is very welcome |
| Hosted control plane, runner agent, tunnels, public preview URLs | Requires hosting, uptime and a security surface that an offline CLI does not have |
| Web dashboard, accounts, teams, sharing, billing | Same — and Loam holds no user state to authenticate |
| Production-data sampling, subsetting, anonymisation | A different and much riskier problem. Loam deliberately touches no real data, which is what makes it safe to run anywhere |
| Migration-safety analysis | Schema diffing and risk scoring is a separate product, not environment creation |
| Flaky-test triage, failure intelligence | Loam does not run tests |

### Two things that are genuinely never happening

**A background daemon.** Commands run and exit. A daemon means lifecycle bugs, stale state, and a
thing to explain.

**Network calls home.** Loam makes no request to any Loam server, and has no telemetry. If you want
usage data from your own runs, that is your `--log` flag to write, not ours to collect.
